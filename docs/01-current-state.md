# 현재 상태 (Baseline Audit)

작성일: 2026-08-28 (Sprint 0~2 완료 시점 기준)

PRD가 요구하는 최종 형태와, 지금 리포지토리에 실제로 존재하는 것 사이의 간극을 정리한다. 스프린트 계획(`03-sprint-plan.md`)은 이 간극을 메우는 순서다. 스프린트가 끝날 때마다 이 문서 전체를 그 시점 기준으로 다시 쓴다(이력은 git으로 추적).

## 구현되어 있는 것

- **알고리즘 검색(기능 A)** — 실제 AI 연동으로 동작한다.
  - `lib/algorithm-catalog.ts`: 정렬/탐색/그래프/트리/동적계획법/그리디/분할정복/백트래킹/문자열/수학/자료구조/배열 전 분야, 82개 항목의 유효 알고리즘 목록(PRD 3.1의 "사전 정의된 유효 알고리즘 집합").
  - `app/api/algorithm/route.ts`: Vercel AI Gateway(`generateObject` + Zod, 모델 `anthropic/claude-sonnet-5`)로 설명·난이도·난이도 근거·사용처·C/C++/Java/Python 코드·관련 알고리즘을 생성. 서버에서 빈 입력(400)과 카탈로그 불일치(404 + 유사 후보)를 AI 호출 전에 차단.
  - `components/language-tabs.tsx`: C/C++/Java/Python 탭. 최초 진입 시 C++ 기본, `page.tsx`의 `preferredLang` state로 세션 내 선택 유지(PRD 3.2). 특정 언어 코드가 없으면(schema상 nullable) 그 탭만 비활성화 + "불러오지 못했습니다" 플레이스홀더(PRD 5.19의 표시 부분만 — 재시도 버튼은 아직 없음).
  - 관련 알고리즘 버튼: 서버가 자기 자신·카탈로그에 없는 id를 걸러서 내려주고(5.10), 클라이언트도 방어적으로 한 번 더 검증해 무효하면 5.3과 동일한 "일치하는 알고리즘 없음" 상태로 전환한다(5.9).
  - `components/algorithm-combobox.tsx`: `page.tsx`가 입력값을 소유하는 controlled 컴포넌트로 리팩터링. 부분 문자열 자동완성 + 편집 거리 기반 유사 후보(`findClosestEntries`).
  - 상태 표시줄: `idle` / `loading` / `success` / `error` / `invalid` 5가지로 분기.
- **검증 완료 범위**: `tsc --noEmit`, `pnpm build` 통과. `POST /api/algorithm`을 node fetch로 직접 호출해 빈 입력(400), 카탈로그에 없는 이름(404 + 추천), 유효한 이름(AI 호출 시도, 키 없어 502)까지 세 경로를 확인.
- **문제 검색(기능 B)** — 이제 실제 AI 연동으로 동작한다.
  - `app/api/problem/route.ts`: `generateObject` + `ProblemAnalysisSchema`로 문제 난이도·근거·매칭 여부(`matched`)·풀이별(algorithmId/해설/시간복잡도/추천 여부) 목록을 생성. `/api/algorithm`과 동일하게 카탈로그에 없는 `algorithmId`는 서버에서 걸러내고, 필터링으로 추천 풀이가 사라지면 첫 풀이를 대신 승격한다.
  - `lib/validation.ts`의 `hasMeaningfulContent`로 5.2(공백/무의미 입력)를 클라이언트·서버 양쪽에서 차단.
  - `components/problem-result.tsx`: 풀이가 여러 개면 탭으로 전환하며 각 탭에 시간복잡도 표시, 새 검색 결과가 오면 추천 탭으로 재초기화, 매칭 없음(`matched:false`)은 오류가 아닌 안내 카드로 정상 렌더링(5.8), 카드 복사 버튼은 활성 탭 내용만 복사.
  - `lib/algorithms.ts`(옛 mock 데이터 파일)는 삭제됨 — 더는 아무 데서도 참조하지 않음.
- **아직 확인 못한 것**: 로컬에 `AI_GATEWAY_API_KEY`가 없어, 알고리즘·문제 검색 모두 AI가 실제로 200을 반환했을 때 화면이 의도대로 채워지는지는 육안으로 보지 못했다. 서버 로직(입력 검증, 에러 코드, 필터링 규칙)은 node fetch로 확인됨.

## PRD 대비 남은 간극

| 영역 | PRD 요구 | 현재 상태 |
|---|---|---|
| 지연/타임아웃 문구 | 3~5초 지연 안내, 15~20초 타임아웃+abort, 무제한 재시도 (5.4, 5.5, 5.6) | 응답이 오래 걸려도 loading만 계속 표시, 타임아웃 없음 — **Sprint 3** |
| 빈 입력 안내 | 경고 문구 + 입력창 포커스·테두리 강조 (5.1) | 빈 값이면 조용히 요청을 안 보낼 뿐, 전용 문구/포커스 이동 없음 — **Sprint 3** |
| 파싱 실패 시 부분 표시 | 있는 필드만 표시, 없는 필드는 플레이스홀더 (5.7) | 현재는 AI 응답이 스키마와 안 맞으면 요청 전체가 502로 실패 — **Sprint 3** |
| 오프라인 감지 | online/offline 이벤트로 문구 전환 (5.12) | 없음 — **Sprint 3** |
| 글자 수 제한 | 카운터 표시 + 초과 시 버튼 비활성화 (5.13) | 없음 — **Sprint 3** |
| 상태 우선순위 규칙 | 여러 예외 동시 발생 시 우선순위대로 단일 문구 (5.18) | 아직 상태 종류가 적어 충돌 사례 자체가 없음 — **Sprint 3** |
| 클립보드 실패 피드백 | 실패 시 토스트 안내 (5.15) | 실패 시 조용히 무시(성공 피드백은 있음) — **Sprint 4** |
| 모바일 레이아웃 검증 | 콤보박스 스크롤, 키보드 회피, 44px 터치 타겟 (5.17) | 반응형 클래스는 있으나 실기기/에뮬레이터 검증 안 함 — **Sprint 4** |
| 언어별 부분 실패 재시도 | 탭 안에 재시도 아이콘, 해당 언어만 재요청 (5.19) | 플레이스홀더 표시까지만 구현, 재시도 버튼/전용 API 없음 — **Sprint 3** |

## 결론

Sprint 0~2로 알고리즘 검색(기능 A)과 문제 검색(기능 B) 두 경로 모두 AI 연동까지 배선이 끝났고, 서버·클라이언트 양쪽의 입력 검증(빈 입력/무의미 입력/목록 불일치/자기참조/매칭 없음)도 확인됐다. PRD 4장의 핵심 파이프라인(입력→검증→AI 처리→출력)은 두 기능 모두 갖춰진 상태다. 남은 핵심 작업은 (1) 5장의 타이밍·오프라인·부분실패 계열 예외를 촘촘히 구현하는 것(Sprint 3), (2) 클립보드·모바일 마감(Sprint 4), (3) AI 성공 응답 렌더링을 실제로 눈으로 확인하는 것(키가 생기는 대로 아무 때나 가능)이다. 다음 착수 지점은 `03-sprint-plan.md`의 Sprint 3.
